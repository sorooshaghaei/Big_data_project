\section{Executive Summary}

This project now has a cleaned Python pipeline, a reproducible Stage 1 method
selection, and five implemented Stage 2 methods aligned with the transport
analytics objective:

\begin{itemize}
\item time variation profiling;
\item weather-impact analysis;
\item ridership forecasting;
\item anomaly detection;
\item contributor ranking and Paris-vs-NYC structural comparison.
\end{itemize}

tables, feature engineering, context enrichment, and PostgreSQL loading hooks.

\texttt{scripts/run\_stage\_workflow.py}.

\section{Objective and Data Sources}

The objective is to use multi-source ridership and validation data to extract
insights, detect patterns, and build predictive models for public transport
usage.

\subsection*{Primary data used}

\begin{itemize}
\item STIF / Ile-de-France rail validations (\texttt{NB\_FER} files)
\item Kaggle Paris/suburbs travel-title validations
\item IDFM surface validations
\item NYC MTA hourly ridership
\end{itemize}

\subsection*{Additional context}

The repository currently does not include a real weather file. The cleaned
pipeline therefore supports two modes:

\begin{itemize}
\item load a real \texttt{data/weather\_daily.csv} file if available;
\item otherwise build a deterministic synthetic weather context for method
validation and report wiring.
\end{itemize}

\section{Stage 2: Implemented Methods}

\subsection*{Method 1: Temporal profiling}

This method answers the demand variation question with:

\begin{itemize}
\item weekday profiles from the enriched daily table;
\item monthly average profiles;
\item yearly totals;
\item NYC hourly totals from the raw MTA file;
\item Paris hourly validation-share profiles from the \texttt{PROFIL\_FER} files.
\end{itemize}

Outputs:

\begin{itemize}
\item \texttt{report/results/temporal\_weekday\_profile.csv}
\item \texttt{report/results/temporal\_monthly\_profile.csv}
\item \texttt{report/results/temporal\_yearly\_totals.csv}
\item \texttt{report/results/temporal\_nyc\_hourly\_profile.csv}
\item \texttt{report/results/temporal\_paris\_hourly\_profile.csv}
\end{itemize}

\subsection*{Method 2: Weather sensitivity regression}

This method aggregates demand to city-day level and fits a linear regression on
log-demand using temperature, precipitation, wind, weekend flag, and month.
This is the correct baseline for answering the weather question before moving
to more advanced causal designs.

Outputs:

\begin{itemize}
\item \texttt{report/results/weather\_regression\_coefficients.csv}
\item \texttt{report/results/weather\_correlations.csv}
\end{itemize}

\subsection*{Method 3: Lag-based random forest forecasting}

This method uses:

\begin{itemize}
\item lag-1, lag-7, lag-14;
\item rolling means and rolling standard deviations;
\item day-of-week, month, and weekend indicators;
\item weather context;
\item categorical one-hot encoding for region, source, and metric type.
\end{itemize}

It performs a time-ordered train/test split and writes holdout predictions and
metrics.

Outputs:

\begin{itemize}
\item \texttt{report/results/forecast\_metrics\_overall.csv}
\item \texttt{report/results/forecast\_metrics\_by\_city.csv}
\item \texttt{report/results/forecast\_predictions.csv}
\end{itemize}

\begin{figure}[htbp]
\centering
\includegraphics[width=0.94\linewidth]{figures/weather_and_forecast.png}
\caption{Weather relationships and forecasting behavior from the current run.}
\end{figure}

\subsection*{Method 4: Hybrid anomaly detection}

This method combines two views of abnormality:

\begin{itemize}
\item a rolling z-score baseline (\(|z| \ge 2.5\));
\item an \texttt{IsolationForest} anomaly detector on value and lag/rolling
features.
\end{itemize}

An observation is flagged if either method detects it.

Outputs:

\begin{itemize}
\item \texttt{report/results/anomaly\_flags.csv}
\item \texttt{report/results/anomaly\_rates.csv}
\end{itemize}

\subsection*{Method 5: Contribution ranking and city comparison}

This method addresses two project questions:

\begin{itemize}
\item Which stations or lines contribute most?
\item How do Paris and NYC differ structurally?
\end{itemize}

It ranks top contributors from the station/line fact table and compares city
totals using average daily demand, variability, weekend/weekday ratio, and peak
month.

Outputs:

\begin{itemize}
\item \texttt{report/results/top\_contributors.csv}
\item \texttt{report/results/city\_structure\_summary.csv}
\item \texttt{report/results/city\_monthly\_structure.csv}

\section{Appendix A: Basics You Need to Understand This Project}

\subsection*{1. What is a fact table?}

A fact table is the main analysis table. Each row represents one measured event
or observation. In this project, the cleaned station fact table stores:

\begin{itemize}
\item a date;
\item a region;
\item a location identifier and name;
\item a source;
\item a metric type;
\item a numeric value.
\end{itemize}

\subsection*{2. Why do we clean raw CSV files before modeling?}

Raw files use different:

\begin{itemize}
\item separators (\texttt{,}, \texttt{;}, tab);
\item date formats;
\item numeric conventions;
\item schemas.
\end{itemize}

If we do not normalize these first, every downstream analysis becomes fragile.

\subsection*{3. What is a lag feature?}

A lag feature is a past value used to predict the future. For example:

\begin{itemize}
\item \texttt{lag\_1}: yesterday's demand
\item \texttt{lag\_7}: demand seven days ago
\item \texttt{lag\_14}: demand two weeks ago
\end{itemize}

These are standard forecasting features because transport demand is strongly
autocorrelated.

\subsection*{4. What is a rolling mean?}

A rolling mean averages the last \(n\) observations. It smooths noise and makes
trend and baseline level easier to model. The project now computes:

\begin{itemize}
\item \texttt{rolling\_7\_mean}
\item \texttt{rolling\_7\_std}
\item \texttt{rolling\_30\_mean}
\item \texttt{rolling\_30\_std}
\end{itemize}

\subsection*{5. What is a z-score?}

A z-score tells you how far one observation is from its rolling baseline in
units of standard deviation. Large absolute values are suspicious and often
indicate spikes or drops.

\subsection*{6. Why random forest for forecasting?}

Random forests are practical because they:

\begin{itemize}
\item work with nonlinear relationships;
\item handle mixed numeric and categorical information;
\item require less tuning than many advanced sequence models;
\item give a strong baseline before deeper time-series models.
\end{itemize}

\subsection*{7. What is Isolation Forest?}

Isolation Forest is an unsupervised anomaly detector. It tries to isolate
observations that look unlike the rest of the data. It is useful when you do
not have labels telling you which events are true anomalies.

\subsection*{8. What is PostgreSQL doing here?}

PostgreSQL is the structured storage layer. Python prepares and enriches the
data, then PostgreSQL stores it so you can query:

\begin{itemize}
\item daily demand;
\item weather-enriched demand;
\item rolling statistics;
\item anomaly-oriented views and joins.
\end{itemize}
